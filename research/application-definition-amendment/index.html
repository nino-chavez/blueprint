Define the whole application before comparing concepts.

Then update that definition after a human chooses a direction, and freeze it before validating or building the selected application.

Why this change

A document can pass the check while the application stays undefined.

The existing Design Principles gate is an individual filename check. In the packet, a lone DESIGN.md passes it; removing that file fails it. That is useful evidence about one gate, not proof that the current pipeline passes or that an application is ready.

Current gate coverage

  1. The design-stage gate looks for a design document
  2. That document can omit a job, permission, or recovery path
  3. No checked definition phase stops concepts from starting early

Proposed order

  1. Existing-product blind baseline review, when relevant
  2. Draft and review the complete application definition
  3. Compare concepts; record the human choice and useful parts retained from other options
  4. Reconcile and freeze the selected definition
  5. Blind validation of the selected candidate, then separately authorized implementation

The earlier blind baseline review looks at the existing product before rationale is shown. The later blind validation looks at the selected candidate. They answer different questions and stay separate. The proposal adds ordered phases inside the design stage instead of a new numbered stage, so existing stage IDs and historical cursors do not move.

What must be defined

Define the rules, screens, and paths.

Use existing sources where they already cover the need. These are required kinds of information, not seven new files. The point is a reviewable connected model, using stable IDs already owned by the project.

Purpose and rulesBusiness requirements (BRD), product requirements (PRD), and user stories connect the problem to product rules and testable acceptance.
Surfaces and behaviorEvery task surface, action, permission, state, transition, feedback, and recovery route has an owner.
Journeys in two formsEach in-scope job has a written path and a diagram of the same IDs, including failure and return.

Applies to: a new application or a whole-application rethink. A whole-app rethink can reference accepted page contracts; it does not require redesigning every accepted page. A bounded preserve/refit is not a fleet retrofit: it carries a reviewed exclusion naming affected surfaces and preserved contracts. If navigation, role boundaries, or lifecycle expand, the scope decision reopens.

Worked miniature example

Show who can save and how to recover.

In the packet’s fixture, a guest’s job is to record their own answer. FR-1 requires it; US-1 describes the authorized guest; P-1 is the invitation surface; and PER-1 decides who may save.

This is synthetic test data, not a real user outcome or product approval. A screen sequence can show “Save” then “Saved” and still be incomplete if it does not name the permission, the state change, and the recovery route that make the sequence trustworthy.

A pass is evidence about this transition only. Drafting permission, concept permission, human selection, product freeze, and build permission are separate facts. One owner message may cover more than one, but the host must verify its scope rather than infer it.

Scope and authority

Each decision authorizes a different step.

  1. Drafting authorityMay investigate and define the bounded application.
  2. Concept authorityMay compare concepts after the draft is current and reviewed.
  3. Human selectionChooses a candidate; it does not approve every product rule.
  4. Product freezeConfirms the reconciled definition used for selected-candidate validation.
  5. Implementation authorityPermits only the separately scoped durable build after its existing technical and validation checks.

Evidence and decision boundary

The prototype blocks the tested omissions. Its product benefit is unmeasured.

Observed in this packet

37 probe controls passed. They cover omissions, stale evidence, synthetic approvals, selection/freeze gaps, exclusions, and separate build authorization. The narrow existing design-document gate is separately observed.

Still unproven

The authority is synthetic. The stage-engine test injects a copied engine only for the experiment. Neither proves shipped phases, a real human-authority adapter, complete real semantics, or better product outcomes.

The prototype also does not decide whether a diagram is understandable to a person. It checks that the fixture’s diagram edges agree with the structured interaction path. A later real pilot must test the proposal against an actual definition, name an omission the ordinary brief would have missed, and compare that benefit with the extra authoring and review work.

What would change the recommendation: an existing accepted source already provides the complete model; a smaller gate enforces both timing boundaries; or a real pilot catches no consequential omission beyond the current brief while adding duplicate maintenance. In each case, reduce the proposal before asking consumers to carry a second, overlapping review obligation in ordinary work.
