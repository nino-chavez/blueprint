# Actionable-frontier follow-up

## Trigger

The prospective version-1 consumer completed its local machine proof and
authored a genuine sandbox authentication boundary. Its final operator outcome
remained downstream of that boundary.

The evaluator selected `implement-or-verify` for the ready human boundary plus
two machine claims that could not run until the boundary completed. The
generated result correctly exposed owners and venues, but it mixed a current
handoff with future work and therefore remained operationally murky.

## Question

Can the recipe selector return only claims on the current actionable dependency
frontier, so a headless initiative presents one honest control boundary at a
time?

## Frozen change

- A ready blocking human claim is selected before downstream blocked human
  outcomes.
- A blocked human or decision outcome resolves its targets recursively to the
  first unresolved claims whose declared dependencies are satisfied.
- Open machine work selects only dependency-ready machine claims.
- If all open machine claims are blocked, their targets resolve to the same
  actionable frontier.
- Version-0 recipe compatibility remains unchanged.

The evaluator still does not infer that a selected claim has been completed.

## Preregistered tests

1. With local proof satisfied, sandbox authentication open, sandbox inspection
   blocked, and final acceptance downstream, select `run-bounded-encounter`.
2. The only target is the sandbox authentication claim.
3. The only next action is the authored external operator route.
4. After sandbox authentication is satisfied, select
   `implement-or-verify` for only the sandbox inspection machine claim.
5. The full suite remains deterministic and contains no absolute user path.

## Distribution ceiling

Passing this follow-up authorizes continued prospective consumer dogfood. It
does not authorize a `template/`, public CLI, or methodology-wave change.
